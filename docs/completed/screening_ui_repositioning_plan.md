# スクリーニング UI の位置づけ変更 計画

**ステータス**: 計画（未実装）
**背景**: [n_pattern_backtest_spec.md §16.2](n_pattern_backtest_spec.md)

---

## 0. 目的

N字スクリーニングを「期待値のあるスクリーナー」から
**「候補を眼で見つけるための発見ツール」**へ位置づけ直す。

バックテストで、スコアにもその構成要素にも前方リターンの予測力が無いことが確定した
（§14.3 / §15.3 / §16）。にもかかわらず現在の UI は **スコア降順で並べ、最小スコアで
絞り込む**構成で、実測の裏付けが無い期待値の含意を読み手に与えている。

**やらないこと**: 検出ロジック（`n_pattern.py`）の変更。検出そのものは
「N字の形をした銘柄を拾う」という宣言どおりに動いており、問題は提示の仕方にある。

---

## 1. 方針

| | 現在 | 変更後 |
|---|---|---|
| 主軸 | スコア（0〜75 の合成値） | **ブレイク日（新しい順）** |
| スコア列 | 表示 | **廃止** |
| 要素の提示 | 合成値に畳み込み | **バッジで個別表示（集約しない）** |
| 絞り込み | 最小スコア（0/50/60/70/75） | **経過営業日（後述）** |

### 1.1 なぜ「改名」で済ませないか

「スコア」を「N字度」に改名するだけの案は採らない。

**今の式は N字らしさを測っていない。** 内訳は `BASE 40 + BREAKOUT 15 + VOLUME 10 +
MACD 10`（`TREND` は 0）で、**加点 35 点のうち 20 点は形状ではなく確認指標**
（出来高・MACD）である。名前を変えても測っているものは名前と違うままになる。

さらに構成要素は個別に無情報だと実測済み（超過リターン基準・日付ブロックブートストラップ）。

| 要素 | 差 | 95% CI |
|---|---|---|
| `sd_breakout` | +0.35% | [-0.20%, +0.91%] |
| `sd_macd` | +0.46% | [-0.32%, +1.26%] |
| `sd_volume` | -0.05% | [-0.57%, +0.54%] |
| `sd_pullback_penalty` | +1.63% | [+0.42%, +2.88%] ← **符号が逆**（減点群のほうが良い） |

**無情報な要素を足し合わせた合成値**を、看板だけ替えて残す理由がない。

## 2. バッジの設計

`score_detail` の 6 要素のうち、実際に情報を持つのは 3 つだけ。

| 要素 | 状態 | バッジ |
|---|---|---|
| `trend` | `TREND_BONUS = 0` のため常に 0 | **出さない** |
| `duration_penalty` | 3 年で発火 1 件（実質死にコード） | **出さない** |
| `breakout` | ブレイク幅 ≥ 5% | 「強いブレイク」 |
| `volume` | ブレイク時の出来高が 20 日平均比 +50% 以上 | 「出来高急増」 |
| `macd` | ブレイク時に MACD が GC 方向 | 「MACD GC」 |
| `pullback_penalty` | 押し目が浅い（`(B-C)/(B-A) < 0.20`） | 「浅い押し目」 |

### 2.1 提示のルール

- **バッジは「パターンの事実」であって「品質の評価」ではない。**
  良し悪しを示す配色（緑/赤）を使わない。数を数えて並べ替えない
- `pullback_penalty` は内部名が「penalty」だが、**実測では減点群のほうが超過リターンが
  高い**。UI では中立に「浅い押し目」とだけ表示する（減点という含意を持ち込まない）
- バッジが 0 個の行も普通に出る。それは「弱い候補」ではなく「その要素が立たなかった」だけ

## 3. 絞り込みの置き換え

**最小スコアフィルタは廃止するが、代わりが要る。**

実測: 1 スキャンで表示される銘柄数は **中央値 143 / 最小 28 / 最大 342**（ユニバース 563）。
`RECENCY_MAX_BARS = 10` により直近 10 営業日以内のブレイクが全部残るため。

なお現行の最小スコアは絞り込みとしても弱い。**スコアは実質 4 値しか取らない**
（50 点 26% / 65 点 43% / 75 点 16% / 60 点 7% で全体の 92%）ため、
`min_score = 65` でも 143 件 → 約 84 件にしかならない。

### 3.1 採用案: 経過営業日での絞り込み

ブレイクからの経過営業日で絞る（`0-2 / 0-4 / 0-10`（既定 0-10 = 全件））。

- **並び順と同じ軸**なので、UI の意味が一貫する
- **期待値の含意を持たない**。「新しいものから見る」は作業順序であって予測ではない
- `RECENCY_MAX_BARS` に対応しており、絞りの上限が実装と一致する
- 「0-2」で概ね 40 件前後に落ちる（週 1 運用で目視できる量）

> **注意**: 経過日数が短いほど有利だという証拠は無い。§14.5 の遅延感応度は
> next_open 2.11% / lag_5 2.34% とフラットだった。**これは鮮度の話であって
> 期待値の話ではない**、と UI 上でも誤解されない表現にする。

## 4. 変更箇所

### 4.1 バックエンド

| ファイル | 変更 |
|---|---|
| `services/screening_provider.py` | `results.sort(key=score, reverse=True)` → **`break_date` の降順**（同着は ticker 昇順で安定化） |
| `routes/screening.py` | `GET /api/screening/n-pattern` の `min_score` クエリを**削除**。フィルタは不要（絞り込みはクライアント側で `break_date` から計算できる） |
| `schemas/screening.py` | 変更なし。**`score` / `score_detail` はレスポンスに残す**（再検証と `scripts/` から使うため） |

`score` をレスポンスから消さないのは、**閾値を戻して再検証する経路を残すため**
（§16 の `TREND_BONUS` と同じ扱い）。UI に出さないだけにする。

### 4.2 フロントエンド

| ファイル | 変更 |
|---|---|
| `components/Screening/ScreeningTable.tsx` | スコア列を削除しバッジ列を追加。ソートを `break_date` 降順に。「ブレイク日」列を追加 |
| `components/Screening/ScreeningView.tsx` | `MIN_SCORE_OPTIONS` を削除し「経過営業日」の select に置換 |
| `hooks/useScreening.ts` | `minScore` / `setMinScore` を `maxAgeDays` に置換。API へは渡さずクライアント側で絞る |
| `lib/screeningApi.ts` | `fetchScreeningResults()` から `min_score` クエリを外す |
| `components/Screening/screening.css` | `.screening-score` を削除しバッジのスタイルを追加 |
| `types.ts` | `ScreeningResult` は変更なし（`score` / `score_detail` は保持） |

**経過営業日の算出**は表示側で行う。営業日の厳密な計算はクライアントに祝日表がないため、
`break_date` と最終スキャン日（`generated_at`）の**暦日差**で近似し、
select の選択肢も暦日で表現する（`3日以内 / 7日以内 / 全件`）。
営業日で厳密にやるならバックエンドが `age_bars` を返すのが筋だが、
**表示順に影響しない**ので初回スコープからは外す。

### 4.3 テスト

| ファイル | 変更 |
|---|---|
| `backend/tests/test_screening_api.py` | `test_scan_sorts_desc_and_applies_filters` を書き換え。**`break_date` 降順**の検証と、`min_score` クエリが無くなったことの確認 |
| `apps/renderer/src/__tests__/` | 並べ替えとバッジ導出は純関数に切り出し（例 `lib/screeningView.ts` の `sortByBreakDate` / `toBadges`）てテストする。コンポーネント自体はテストしない（既存の方針に合わせる） |

## 5. 実装順序

1. `screening_provider` の並び替えを `break_date` 降順に変更 + pytest 更新
2. `routes/screening.py` から `min_score` を削除 + pytest 更新
3. `lib/screeningView.ts`（新規）に `sortByBreakDate` / `toBadges` を純関数で実装 + vitest
4. `ScreeningTable.tsx` — スコア列削除、ブレイク日列とバッジ列を追加
5. `ScreeningView.tsx` / `useScreening.ts` / `screeningApi.ts` — フィルタ置換
6. `screening.css` — バッジのスタイル
7. `npm run typecheck` / `npm run test:renderer` / `cd backend && pytest`
8. `CLAUDE.md` の該当記述（`MIN_SCORE_OPTIONS` に言及している箇所）を更新

## 6. 決定事項

- **絞り込みの既定値は「全件」**。既定で絞ると見落としが出るため。
  スクロールが長くなる代償は受け入れる（選択肢で絞れる）
- **経過日数は暦日で近似**する。営業日で厳密にやるならバックエンドが `age_bars` を
  返すのが筋だが、**表示順には影響しない**ためスコープ外
- **サムネイルは今回は変更しない**。発見ツールとしては主役になり得るが、別タスク
- **バッジは 4 種**（`trend` と `duration_penalty` は出さない）。前者は常に 0、
  後者は 3 年で 1 件という実測に基づく。`TREND_BONUS` を将来戻すなら
  バッジも併せて復活させる
