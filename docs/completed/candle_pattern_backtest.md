## 0. 目的とスコープ

チャート上に表示しているローソク足パターン（`apps/renderer/src/lib/candlePatterns.ts`）に、
前方リターンの予測力があるかを実測する。N字の検証（[n_pattern_backtest_spec.md](n_pattern_backtest_spec.md)）で
作った OHLCV ストアと統計の枠組みをそのまま流用する。

きっかけは「日足で明けの明星が出た後、1週間後・2週間後の勝率を見たい」という問い。
2026-07 に 7 パターンで測って全否決し、その後 7 種を追加して 14 パターンに増えたため、
2026-08 に**全種を測り直した**のがこの文書の §3 以降である。

## 1. 実装構成

既存の「`analysis/` は純関数・I/O なし / `scripts/` が I/O と探索」という分離を踏襲する。

```
backend/src/analysis/candle_patterns.py   検出器（純関数・14パターン）
scripts/candle_backtest.py                OHLCV 読み込み・前方リターン・ランダム比較・集計
backend/tests/test_candle_patterns.py     84 件
```

### 1.1 定義はレンダラーと一致させる

閾値（`DOJI_BODY_RATIO=0.1` / `HAMMER_LOWER_RATIO=2.0` / `HAMMER_UPPER_RATIO=0.25` /
`STAR_BODY_RATIO=0.3` / `HARAMI_BODY_RATIO=0.3` / `SIDE_BY_SIDE_OPEN_TOLERANCE=0.005` /
`HAMMER_TREND_LOOKBACK=10` / `HAMMER_TREND_RATIO=0.05` / `ISLAND_MAX_LEN=5`）と
ロジックは `candlePatterns.ts` と同値。

**チャートに描かれるものと検証対象がズレると、検証結果を UI に持ち込めない。**
片方だけ変更してはいけない（変更時は両方 + テストを揃える）。

TS 側に無い `shooting_star` は既存検出器の厳密な鏡像として定義した。**鏡像関係は定数を
書き下すのではなく価格反転（x → -x）でテストしている** — 定義がズレたらテストが落ちる。

**鏡像ペアは 4 つ**（はらみ / 包み / 明星 / アイランド）。**ハンマーと首吊り線は
鏡像ではない** — 形状が完全に同一で、トレンド文脈だけが違う。価格反転すると形状が
流れ星型になる一方、騰落率は分子・分母が同時に符号反転して値が変わらないため、
反転では入れ替わらない（ハンマーの幾何的な鏡像は `shooting_star`）。この 2 種は
価格反転テストではなく排他テストで担保している。

**トレンド文脈のしきい値は日足で較正してある。** `HAMMER_TREND_LOOKBACK = 10` /
`HAMMER_TREND_RATIO = 0.05`（10 本の騰落率で ±5% が概ね 1σ 強）は日足の値幅を前提に
決めた。判定は「本数」ベースでタイムフレームに依存しないため、UI が 5m〜1M で
同じ検出器を走らせると、**分足ではハンマー/首吊り線がほぼ出ず、月足ではほぼすべての
ハンマー型がどちらかに分類される**。この検証と下の実測値はすべて日足のもので、
他のタイムフレームでの較正は行っていない。

**トレンド文脈を見るのは `hammer` / `hanging_man` だけ。** 同型の文脈問題を持つ
`shooting_star`（流れ星／逆ハンマー）は形状のみのままにしてある — UI に出していない
検出器を変更してもユーザーに見える利得が無いため（Phase 6 で解消予定）。
Python 内にこの非対称が残っていることを前提にコードを読むこと。

### 1.2 明星の窓（ギャップ）

古典的な明けの明星は「星が 1 本目の実体より下に窓を開ける」ことを要求するが、
**既定は窓を要求しない**（TS 側の宵の明星に合わせるため）。`--require-gap` で厳密版になる。

**窓の基準はコード内に 2 種類ある。** `require_gap` は**実体基準**（星の実体が 1 本目の
実体の外にあるか）だが、`has_gap_up` / `has_gap_down`（下放れ二本黒・上放れ並び赤・
アイランドが使う）は**高安基準**（ヒゲを含めて重ならない）。見た目の「窓」と一致するのは
後者で、前者は既定 off・UI 経路では未使用のため統一していない。

### 1.3 実装上の注意

- **ランダム母集団は全パターン共通で 1 回だけ抽出する**。パターンごとに引き直すと
  同じ日の帰無分布がパターン間で食い違い、横並び比較が成立しない。
  **1 run = 1 表**。表をまたいでセル単位の比較をしない
- **銘柄ループを外側にする**。パターンごとに全銘柄を読み直すと Parquet の I/O が
  パターン数倍になる
- entry は成立バーの**翌営業日始値**、リターンは `close[j+h] / open[j] - 1`。
  `backtest.benchmark_outcome` と同じ規約に揃える（土俵を揃えないと比較できない）
- **`--seed` を既定の 0 から動かさない**。理由は §7（品質フィルタがランダム側に
  掛かっておらず、シード次第で表が壊れる既知の欠陥がある）

## 2. 生の勝率を単独で出してはいけない

**2021〜2026 の日本株では、どの銘柄でもいいから 10 日持てば勝率 53〜55% になる。**
市場が上がっているからである。

実測した 14 パターン 56 行の生の勝率は **46.7%〜63.4%**。50% を下回ったのは
**首吊り線の前期 2 行だけ**で、残り 54 行は 50% を超えた。
ランダム比を取らないバックテストツールなら、そのほぼ全部を「有効なシグナル」として報告する。

例:

- 明けの明星 fwd10 は勝率 54.7%。しかし同日ランダムは 55.5% で**負けていた**
- ハンマー fwd10（後期）は勝率 **63.4%** で全 56 行の最高値。ランダムは 56.6% で
  確かに上回っているが、**この差はローソク足の形が生んだものではない**（§4）

→ `scripts/candle_backtest.py` は生の勝率とランダム勝率を必ず並べて出力する。

### 3.3 再現性の点検（定義未変更の 6 種）

`doji` / `bullish_engulfing` / `bearish_engulfing` / `shooting_star` / `morning_star` /
`evening_star` の 6 種は Phase 1〜3 で定義を変えていない。2026-07 の 7 パターン run と
今回の 14 パターン run で、**前期・後期あわせて 24 行すべてが n・勝率・差・CI まで完全に一致した。**

これは自明ではない。`random_returns` は run 内の全シグナル日を昇順に舐めながら単一の
`random.Random(seed)` を消費するため、run に含まれるパターンが変わって日付集合が
変われば、以降の抽選がすべてずれる。24 行が一致したのは、**同時線が事実上すべての
営業日に出るので日付集合が両 run で同一だった**ことによる。

パターンを絞って走らせた表を、絞らずに走らせた表と比べるときはこの前提を確認すること。

## 4. ハンマー/首吊り線の有意差はどこから来たか

§3 で ★ が付いた 4 行（後期のハンマー 2 行・前期の首吊り線 2 行）は、この 3 年で
初めて「パターンの向きと符号が一致した有意差」だった。**しかし原因はローソク足の形ではない。**

`hammer` = 「ハンマー型の形状」かつ「直前 10 本で -5% 以上の下降」である。
条件が 2 つあるので、形状・文脈のどちらが効いているのかを分けて測った。

### 4.3 では何を測っていたのか

`HAMMER_TREND_RATIO = 0.05` の条件は、実質的に「直近 10 本で 5% 下げた銘柄を翌日の
寄りで買う」という**短期リバーサル**のフィルタである。ランダム比較の相手は
「同じ日に無条件でランダムに買う」なので、下げた銘柄に絞った時点で差が出る。

これは既知の市場効果であって、ローソク足パターンの検証結果ではない。
[backtest_gotchas.md](backtest_gotchas.md) の
「要素の発火は相場局面と相関するため、生リターンでは要素が効いたのか地合いが良かったのかを
分離できない」と同じ構図が、ここでは「文脈条件」と「形状条件」の間で起きていた。

### 4.4 Phase 3 の仮説はどう決着したか

「旧ハンマーが前期で負に有意だったのは、上昇後の首吊り線を混入させていたからではないか」
という仮説（PRD Q1 / Technical Risks）は、**現象としては支持された**。

- 旧定義（形状のみ）前期: -0.24% ★ / -0.27% ★
- 三分化後のハンマー 前期: +0.19% / +0.39%（★ が消え、符号も反転）
- 三分化後の首吊り線 前期: -0.44% ★ / -0.79% ★（弱気パターンとして符号も正しい）

負の寄与は上昇文脈側に集まり、ハンマーからは消えた。**三分化は表示の正しさとしては正解**である
（上昇後のハンマー型に強気ラベルを出すのは、実測でも間違いだった）。

ただし §4.2 のとおり、分離できた理由は形状ではなく文脈条件そのものにある。
**「ハンマーに予測力があることが分かった」と読んではいけない。**

## 5. 結論

**14 パターンすべて否決。ローソク足の形状に前方リターンの予測力は無い。**

56 行（14 パターン × 2 ホライズン × 2 期間）のうち CI が 0 を外れたのは 5 行。
α=0.05 での偽陽性期待値 2.8 に対し実測 5 で、内訳は次のとおり。

| 行 | 判定 |
|---|---|
| 後期ハンマー 2 行 | **形状ではなくトレンド文脈（短期リバーサル）由来**（§4）。形状の増分は CI が 0 を跨ぐ |
| 前期首吊り線 2 行 | 同上。上昇文脈のみでも -0.39% ★ / -0.72% ★ が出る |
| 前期下放れ二本黒 1 行 | 弱気パターンなのに**符号が逆**。後期では有意性が消える。偶然の出方 |

**形状の増分だけを測った 8 行では、有意なのは「形状があるほうが悪い」2 行だけで、
その符号も期間をまたぐと反転する。** N字の検証（§15.3）や旧ハンマーで見たのと同じ現象である。

この結論は UI の方針を変えない。パターン表示の立場は**中立な観察ツール**であり
（PRD Decisions Log「表示の立場」）、予測力の有無で表示を止める設計ではない。
**否決だからマーカーを消す、という話にはならないし、逆に有意だから勝率を出す、という話にもならない。**

## 7. 既知の欠陥: ランダム側に品質フィルタが掛かっていない

`collect_signals` はシグナル側に品質フィルタを掛ける（`has_non_positive_prices` /
`sanity_check` で 3 銘柄を除外）が、`random_returns` には**同じフィルタが無い**。

**これはシードに依らない母集団の不一致である。** シグナル側は 562 銘柄、ランダム側は
565 銘柄で、比較の土俵がそもそも揃っていない。そのうえで、引きが悪いと表が桁ごと壊れる。

実害は 8303（上場廃止・再上場を跨いだ系列）で、fwd10 の最大値が **+1,979,956,997%** ある。
この 1 サンプルがどこかの日付で引かれると、その日の帰無平均が桁ごと壊れる。

再現（後期・同時線・fwd10）:

| seed | 差 | 95% CI |
|---|---|---|
| 0（既定・本文の測定） | +0.07% | [-0.12%, +0.26%] |
| 1 | **-445298.71%** | **[-1335896.32%, +0.19%]** |
| 2 | +0.00% | [-0.20%, +0.22%] |
| 3 | +0.11% | [-0.10%, +0.31%] |

**§3〜§6 の測定は seed 0 で、8303 の壊れたバーは引かれていない。** 根拠は
**差の列が全 56 行で ±1.5% に収まっていること**の 1 点に尽きる。あの 1 サンプルが
入れば帰無平均が桁ごと動き、seed 1 のように差が数十万 % になって一目で分かる。

**次の 2 つは根拠にならない**（どちらも最初に書いてしまい、レビューで否決された）:

- **ランダム勝率が 52〜57% に収まっていること** — 勝率は `> 0` を数える符号統計で、
  +1,979,956,997% も +0.1% も 1 勝としか数えない。**外れ値では壊れないので検出できない**
- **§3.3 で 24 行が完全一致すること** — 2026-07 の測定も同じ seed 0・同じ日付集合で
  走っている。**同じように汚染されていても一致する**ので、汚染の不在を示さない

母集団の不一致（562 対 565）のほうは seed 0 でも残っており、**こちらは上の根拠では
否定できない**。3 銘柄が混じる影響は小さいと見ているが、測っていない。

[backtest_gotchas.md](backtest_gotchas.md) は「品質フィルタは N字側とランダム側の両方に
掛ける」と明記しており、`backtest_report.py` では対処済みだが、
**`candle_backtest.py` には同じ修正が入っていない。** 修正すればランダム母集団が変わり
§3 以降の数値がわずかに動くため、この検証と同じコミットでは直していない（別途対応する）。

## 8. 再現方法

```bash
python scripts/candle_backtest.py --horizons 5,10 --start 2023-07-01                    # §3.1
python scripts/candle_backtest.py --horizons 5,10 --start 2021-08-01 --end 2023-06-30   # §3.2
# §3.4（古典的定義・前期）。--patterns で絞ると帰無分布が変わるので §3.1/3.2 とは別の run になる
python scripts/candle_backtest.py --patterns morning_star --require-gap \
  --horizons 5,10 --start 2021-08-01 --end 2023-06-30
```

- OHLCV ストアが前提（`python scripts/backtest.py fetch --period 5y`）
- 測定日 **2026-08-09** / ストアは 2021-07-27 〜 **2026-07-29** / ユニバース 565 銘柄中 **562 銘柄**が有効
- **`--seed` は既定の 0 のまま使う**（§7）
- `--patterns` を省略すると 14 種すべてが 1 回の run に入る。**絞ると帰無分布が変わる**（§1.3 / §3.3）
- §4 と §6 の測定はスクリプト化していない。`candle_patterns._hammer_shape` /
  `trend_change_ratio` のマスクを `collect_signals` と同じ規約で集計し、
  `candle_backtest.compare` の対照群引数に渡すだけで再現できる
  （`compare(sig, rnd, h)` の `rnd` は `{日付: [リターン]}` なので、ランダム以外の対照群も渡せる）

## 9. 新しいパターンを足すとき

1. `analysis/candle_patterns.py` に検出器を書く（純関数・bool 配列を返す・複数バー構成は
   **最終バー位置**に True）
2. `DETECTORS` / `LABELS` / `SIGNALS` の 3 つに登録する
   （テスト `test_labels_and_signals_cover_every_pattern` が揃っていることを保証する）
3. UI にも出すなら `candlePatterns.ts` を同じ定義・同じ閾値で更新する
   （手順の全体は [CLAUDE.md](../CLAUDE.md) の「ローソク足パターン」節）
4. `scripts/candle_backtest.py` は引数を増やさずそのまま使える

**生の勝率だけで判断しないこと。** この銘柄群・この期間のベースレートは 53〜55% で、
それを明確に超えないパターンは情報を持っていない。

**条件を 2 つ以上持つ検出器を足したら、条件ごとに分けて測ること**（§4）。
形状 + 文脈のように条件を重ねると、どちらが効いているのか合成後の数字からは分からない。
