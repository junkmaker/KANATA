# PPP の増分測定 設計メモ

[ppp_screening_spec.md](completed/ppp_screening_spec.md) で決めた PPP 検出器を、CLAUDE.md の
「**条件を 2 つ以上持つ検出器を足したら、条件ごとに分けて測ること**」に従って検証する
ための設計。**実装・リリースの前提条件ではない**（表示は検証を待たない）。

前提の統計・データ品質の罠は [backtest_gotchas.md](completed/backtest_gotchas.md) に集約済み。
本書はそれを繰り返さず、**PPP 固有の設計判断**だけを書く。

---

## 1. なぜ増分測定が要るのか

PPP はハンマーと**構造が同型**である。

| | 条件A（形状的） | 条件B（量的） | 起きたこと |
|---|---|---|---|
| ハンマー | ハンマー型の形状 | 直前 10 本で -5% 以上の下降（`HAMMER_TREND_RATIO`） | 有意差は**条件B 由来**だった。形状の増分は 8 行中 6 行で CI が 0 を跨ぎ、残る 2 行は形状があるほうが**悪い**（[candle_pattern_backtest.md](completed/candle_pattern_backtest.md) §4） |
| PPP | `sma5 > sma25 > sma75` の並び | 乖離 `gap / ATR >= k` | **未測定** |

ハンマーで起きた取り違えは「パターン全体 vs ランダム」で測ったために、
条件B が持ち込んだ既知の市場効果（短期リバーサル）をパターンの成果として読んでしまった、
というものだった。PPP を「PPP成立 vs ランダム」で測ると、**同じ取り違えがほぼ確実に起きる** —
PPP は定義上「上昇トレンドにある銘柄」を選ぶので、トレンドフォローの既知効果が
そのまま差として出る。それは PPP の検証結果ではない。

---

## 2. 条件の構造：交差ではなく入れ子

ハンマーの形状／文脈は**交差**していた（形状のみ・文脈のみ・両方、の 3 群を作れた）。
PPP は違う。

```
gap >= k  かつ  k > 0   ⇒   gap > 0   ⇒   並びが成立している
```

**`gap` は 2 本ある。** 実装（`analysis/ppp.py` の `compute_gaps`）は
`gap_short = (sma5 - sma25) / atr` と `gap_long = (sma25 - sma75) / atr` を別々に返し、
成立は「**同一バーで両方が k 以上**」である。本書で `gap >= k` と書いたものはすべて
この意味で、「どちらかがいつか到達した」ではない。群分けを実装するときに
取り違えると、処置群に本来入らない局面が混ざる（§3 を参照）。

**乖離条件は並び条件を含意する。**「乖離は満たすが並んでいない」群は存在しない。
したがってハンマーで使った 2×2 の分解はそのまま使えず、**入れ子（nested）の増分**として
測ることになる。具体的には次の 2 つを別々に測る。

- **§4.1 並びそのものに情報があるか** — 対照はランダム（＝ハンマーの「形状のみ」に相当）
- **§4.2 乖離 `k` に増分があるか** — 対照は「並びは成立したが `k` に届かなかった群」

§4.2 が本丸である。§4.1 だけで有意差が出ても、それは「上昇トレンド銘柄を買った」以上の
ことを言っていない可能性が高い。

---

## 3. 群の定義

`k = 0` かつ `k_exit = 0` の素朴な状態機械（並びの成立初日を拾うだけ）を **S**、
その局面のうち乖離が `k` まで広がったものを **P** とする。**`k_exit` は 2 群の
どちらでも 0 に固定する**（理由は下の注意書き）。

| 記号 | 定義 | 役割 |
|---|---|---|
| **S** | 並びの成立イベント（`k = 0, k_exit = 0`） | §4.1 の処置群 |
| **P** | S の局面のうち、**局面中に `gap_short` と `gap_long` が同一バーで `k` 以上に達した**もの（`k_exit = 0` で判定） | §4.2 の処置群 |
| **S \ P** | 並びは成立したが、その成立局面で一度も `k` に届かなかったもの | §4.2 の対照群 |
| **R** | ランダムエントリー（ユニバース全体から日付を引く） | §4.1 の対照群 |

**P は「本番設定（`k_exit = 0.5`）の実イベント」ではない。** §4.2 では `k_exit = 0` に
固定して `k` だけを振る。両者は一致しないので、混ぜると処置群が壊れる —
`-k_exit < gap < 0` の浅い押しは `k_exit = 0` では崩壊（＝局面の切れ目）になるが、
本番設定では `state` が `in` のままなので、次に `k` を上抜けても
イベントが出ない（`analysis/ppp.py` の状態機械）。ローカルストア 566 銘柄
（1 銘柄あたり中央値 1225 バー）で実測すると、S 局面 13112 のうち `k = 1.0` へ
到達したのは 6932、本番設定の実イベントは 5901 で、**到達局面の 14.9%（1031 件）に
対応する実イベントが無い**。

`k_exit` を 0 に固定するのは測定上の要請であって本番設定の否定ではない。
`k_exit` が何をしているかは §4.3 が別に測る。この分離により §4.2 は
「乖離 `k` の増分」だけを、`k_exit` の効果と混ざらない形で見ることになる。

**S \ P の作り方に注意。** 素朴に「S のイベント日に `gap < k` だったもの」とすると、
成立初日は必ず `gap ≈ 0` なので **S のほぼ全件が対照群に入る**（P のイベント日は
`gap` が `k` を上抜けた日で、S のイベント日より後ろにずれる）。そうではなく、
**S の成立から次の崩壊までを 1 つの局面として扱い、その局面中に `gap` が `k` 以上へ
到達したかどうかで S を二分する**。到達した局面は P、しなかった局面が S \ P。

この定義だと P のイベント日（`k` 到達日）と S \ P のイベント日（並び成立日）で
**日付の意味が揃わない**。揃えるために、**両群ともイベント日を「局面の開始日（＝並び成立日）」に
固定する**。こうすると測っているのは「並びが成立した局面のうち、後に十分な乖離まで
広がるものは、そうでないものより最初から良いか」という問いになる。

**この設計の答えは取引可能な主張ではない。** 局面の開始日の時点では、その局面が後に
`k` へ到達するかどうかは分からない（＝群分けに未来の情報が入る）。検出器そのものは
因果的（§5）だが、**この測り方で出た差を「PPP を買えば取れる差」と読んではいけない**。
レポート本文にこの一文をそのまま書くこと。

> 別解が 2 つある。**どれを採ったかを必ずレポート本文に書くこと**（結論の意味が変わる）。
>
> - **ラグ対応付け**: P のイベント日を `k` 到達日のままにし、対照群には
>   「S \ P の局面の開始から**同じ本数 L だけ後ろのバー**」を割り当てる。P が
>   開始 +L で到達したなら対照も開始 +L を見る、という対応なので恣意的にならず、
>   処置群側は取引可能な日付のまま測れる
> - **連続量で見る**: 群を切らず、局面内の各バーについて `gap` と前方リターンの関係を
>   直接見る。§4.2 が求めている「`k` に対する単調性」を閾値を切らずに測れる形で、
>   `TREND_BONUS` を反転させなかったときの判断基準（連続量と単調な関係があるか）と
>   同じ土俵になる

## 4. 測定

### 4.1 並びそのものに情報があるか

- 処置群 **S**、対照群 **R**
- 指標は**超過リターン**（対 1306）。生リターンで見ないのは、並びの成立が相場局面と
  強く相関するため（地合いが良い時期に一斉に成立する）。ただし対照が**同じ日の**
  ランダムエントリーである時点で地合いはすでに大部分が相殺されており、超過にして
  さらに落ちるのは「日ごとの件数が 2 群で違うぶん」だけである（ローソク足 14 種の
  測定は生リターン + 同日ランダムで通した）。**超過を採るなら §5 のベンチ汚染マスクを
  必ずセットにする** — ベンチは全行の超過に入る単一障害点で、実測で集計の符号を
  裏返したことがある
- 日付ブロックブートストラップ、再抽出単位は**日付**

**この行に有意差が出ても、PPP の成果とは呼ばない。** 「上昇トレンドの銘柄を買った」
という既知の効果と区別できていないため。§4.2 の結果とセットでしか解釈しない。

### 4.2 乖離 `k` に増分があるか 【本丸】

- 処置群 **P**、対照群 **S \ P**（§3 の定義に従い、両群ともイベント日は局面の開始日）
- `paired_block_bootstrap_diffs` で差を直接求める（点推定の目視比較で終わらせない —
  [candle_pattern_backtest.md](completed/candle_pattern_backtest.md) §4.1 → §4.2 で必要になった手順）
- **`k` を 1 点で測らない。** 0.2 刻み程度で振り、増分が `k` に対して単調かを見る。
  単調でないなら、有意に見える点があってもそれは in-sample への当てはめである
  （`TREND_BONUS` を符号反転させなかったのと同じ判断基準：連続量との単調な関係が
  無いなら、閾値付近の二値でしか成立しない）
- **`k` を振るあいだ `k_exit` は 0 のまま**にする（本番の `k_exit = k / 2` に連動させない）。
  連動させると局面の切れ目そのものが `k` ごとに動き、処置群も対照群も同時に変わって
  単調性が読めなくなる

### 4.3 ヒステリシス `k_exit` は何をしているか

`k_exit` はイベントの**選別**しかしていない（`k_exit` を上げると再成立イベントが消える）。
したがって測るべきは「`k_exit` によって**消えたイベント**の前方リターンが、残ったものと
違うか」である。

- 群1 = `k_exit > 0` で残るイベント、群2 = `k_exit = 0` のとき**追加で出る**イベント（＝消える分）。
  この差分は well-defined である — イベント集合は `k_exit` について単調で、
  `k_exit = 0` の集合は `k_exit > 0` の集合を必ず含む（`k_exit > 0` で崩壊したバーは
  `k_exit = 0` でも崩壊しており、その後の初到達日は両者で同じになる）
- 差が 0 を跨ぐなら、**`k_exit` の効果は表示件数の削減だけ**である。それは Q3 で
  意図した効果そのものなので、採用の理由としては十分。ただし
  「ヒステリシスによって質の高いイベントだけが残る」とは**言えない**ので、
  UI にも本書以外にもその含意を書かないこと

### 4.4 期間分割

前期・後期の 2 期間に分けて必ず両方出す。ハンマーの増分は
**期間をまたいで符号が反転した**（後期 +0.15% / +0.38%、前期 -0.51% / -0.60%）。
片方の期間だけ見ると「効いている」と読める行が作れてしまう。

## 5. 実装メモ

- **ウォークフォワードは不要。** PPP の状態機械は因果的なので、`walk_forward_signals` の
  ように `df.iloc[:t+1]` で再実行する必要がない。1 回の前方パスで全イベントが出る（O(n)）。
  因果性は**テストで固定済み**（`backend/tests/test_ppp.py` の
  `test_causality_prefix_reproduces_events` が、prefix を切って再実行した結果と
  全期間結果の絞り込みの一致を全バーで確認する）。状態機械を触るときはこのテストを消さない
- **局面の列挙は新しい純関数が要る。** `ppp_events` は遷移日（`{index, date}`）しか
  返さないので、§3 の群分けに必要な「開始 / 崩壊 / `k` 到達」の 3 点を持つ局面リストが
  取れない。`analysis/ppp.py` に `ppp_phases(df, k) -> [{start_index, start_date,
  end_index, reached_k, reached_index}]` 相当を足し、`ppp_events` と**同じ状態機械の
  実装を共有させる**（別実装を書くと §3 の食い違いが再発する）
- `resolve_entries` / `compute_outcomes` / `benchmark_outcome` /
  `paired_block_bootstrap_diffs` は**そのまま使える**（確定済みイベント日を受け取るだけの
  設計になっている）。②検出と③アウトカムの分離は崩さない
- `mark_overlaps` はキーの変換が要る。`symbol` と `detected_date` を読む実装なので、
  局面リストをその形へ写してから渡す
- **超過リターンを使うなら**（§4.1）、`contaminated_entry_dates` と
  `backtest_report.benchmark_bad_dates` も必須。ベンチ 1306 の 2026-03-30/31 の
  スケール異常が集計の符号を裏返した実績がある（[backtest_gotchas.md](completed/backtest_gotchas.md)）
- **品質フィルタと重複除外は P と S \ P の両側に同じパスで掛ける。** 2 群は S の
  入れ子分割なので、**S 全体に対して 1 回だけ** `mark_overlaps` を回してから分割する。
  群ごとに別々に回すと除外パターンが 2 群で食い違い、ペアードブートストラップの
  前提（同じ母集団の上での差）が壊れる
- 重複シグナルは `mark_overlaps` で `overlaps_prev` を立てるだけにし、除外は集計側で行う。
  **重なりが効くのは P ではなく S の側**である — 実測（566 銘柄）で連続イベントの間隔は
  P が中央値 81 バー・`OVERLAP_BARS = 20` 以内は 3.0% にすぎないのに対し、
  §4.2 が実際に扱う S 局面は中央値 34 バー・20 バー以内が **29.0%** を占める
- `analysis/` に I/O を持ち込まない（`os` / `pathlib` / `yfinance` / `json` を import しない）。
  依存方向は `scripts/ → services/ → analysis/` の一方向

## 6. 事前に決めておく判定基準

結果を見てから基準を作らないために、**測る前に**ここを固定する。

- **前方ホライズン**: 20 / 60 営業日（`backtest.FWD_HORIZONS`）。ローソク足の測定は
  5 / 10 だったが、PPP の保有想定はトレンドフォローで長いほうに寄る。**測ってから
  選ばない** — 前例が 2 系統あるので、後から採ると多重比較になる
- **エントリー種別**: `next_open`（イベント日の翌営業日始値）1 本。`weekly` / `lag_k` は
  感応度の確認として出してもよいが、**判定は `next_open` だけで行う**
- **増分なし**と判定する条件: §4.2 の差の 95% CI が 0 を跨ぐ
- **不安定**と判定する条件: 前期と後期で差の符号が反転する
- **「増分なし」と「検出力が無い」を区別できる形で報告する。** 上の 1 つ目は帰無仮説の
  受容を事前登録しているので、規模を併記しないと後から検証できない。**両群の n・
  distinct な日付数・CI 幅を必ず表に出す**こと。実測（566 銘柄・1 銘柄あたり中央値
  1225 バー）では P 5901 件 / 1058 日、S \ P 6180 件が見込め、§4.4 で期間分割しても
  ハンマーの増分測定（n ≈ 4000 で CI 幅 ±0.45%）と同程度の規模になる。**この水準を
  大きく下回ったら「増分なし」ではなく「測れなかった」と書く**
- **勝率を単独で出さない**（[candle_pattern_backtest.md](completed/candle_pattern_backtest.md) §2）。
  超過リターンの差と CI をセットでしか報告しない
- **否決されても表示はやめない。** 立場は中立な観察ツールであり、N字もローソク足 14 種も
  否決後に表示を続けている。否決の結果として変えるのは「UI に期待値の含意を持ち込まない」
  ことの徹底であって、機能の削除ではない
- 逆に**有意な増分が出た場合**も、UI に勝率・期待値・順位付けを持ち込まない。
  `TREND_BONUS` の経緯（最大の重みを持ちながら符号が逆だった）と、ハンマーの経緯
  （形状に見えたものが条件由来だった）の両方が、単発の有意差を UI 化する判断の
  危うさを示している。表示を変えるなら**再現性の点検を別期間で通してから**

---

## 7. この測定で答えが出ないこと

- **N字との共起に意味があるか**。本書の枠組みは PPP 単独の条件分解であって、
  パターン間の相互作用は扱わない。共起バッジを UI に出すなら、共起群を処置群、
  「片方のみ」を対照群として別途 §4.2 と同じ形で測ること
- **`k` の運用値の妥当性**。`k` は表示件数という運用上の制約で決める
  （[ppp_screening_spec.md](completed/ppp_screening_spec.md) §5.1）。§4.2 で有意な増分が出たとしても、
  それを根拠に `k` を選び直すと in-sample への当てはめになる
